# repo-governance 实测记录

三个轮次、六个真实开源仓库的浅克隆、八个干净上下文的子代理。本文是 skill 迭代
的完整留痕：每轮发现、每条修复的对应关系、以及仍开放的观察项。

## 方法论：执行者与检测者分离

skill 的作者（或参与过其迭代的会话）亲自执行，测不出 skill 对新会话是否友好——
那是「带着答案考试」。因此：

- **执行**：每个仓库由一个全新子代理治理，只拿到 skill + 仓库路径 + 一句用户级
  指令（「使用 repo-governance skill 给这个仓库上治理」），不知晓任何评审结论。
- **核验**：主会话不插手执行，事后只认命令输出与 git 历史（门禁 PASS、上游文件
  零改动、两段式提交、工作区干净）。
- **专项**：退出条款自测（对已治理仓库重发治理指令，必须零改动退出）；冷启动
  三问（新会话只靠仓内文档回答：有无进行中任务 / 最近否决案与重开条件 / 改某类
  bug 从哪下手）。
- **负例注入**：治理收尾前故意造违规（孤儿卡、终态滞留顶层），确认门禁 FAIL
  而非摆设。

测试矩阵按三个维度选仓：运行时（JS / Python / Go / Rust / 纯文档）、既有治理
（裸仓 / 成熟仓 CONTRIBUTING+CI / 已有任务文件体系）、规模。

## 第一轮：husky / click / SDD-Lite

| 测试 | 结果 |
| --- | --- |
| husky（JS 主路径：npm scripts 复用 + CI 接线） | ✅ 全闭环 |
| click（Python：check-docs.py + pytest） | ✅ 全闭环，自发做了负例注入 |
| SDD-Lite（已有 docs/tasks 体系的边界仓） | ✅ 全闭环，产品文件零改动 |
| 退出条款自测（husky） | ✅ 零改动退出，主动拒绝顺手改 |
| 冷启动三问（click） | ✅ 三问全对、链接全通 |

P0 缝隙四条（三仓复现）及修复：

1. **`docs/` 双语义冲突**：现实仓库 `docs/` 常是 VitePress/Sphinx 站点源或分发面，
   skill 原假设它空闲 → 摸底增加用途排查，处理分支详见
   [references/repo-shapes.md](../references/repo-shapes.md)。
2. **两段式提交时序空白**：活跃态卡必须出现在提交 1（否则该提交点位孤儿检查
   FAIL）——原是执行者从门禁行为反推的隐含约束 → 明文写入 development.md。
3. **禁推克隆的 CI 死配置**：「有 CI 就挂」在永不 push 的克隆上等于永不运行的
   配置 → 区分可推送仓（挂 CI）与只读克隆（决策记录 + 待办，重开条件 = fork）。
4. **既有红**：上游自带检查项对 HEAD 零改动报错时，收进门禁等于永远红、逼人
   绕过 → 硬规则：总门禁必须当前可绿，既有红登记待办。

## 第二轮：duf / bat（P0 修复验证）

| 测试 | 结果 |
| --- | --- |
| duf（Go，无任何门禁命令，从零自举 gate.sh） | ✅ 全闭环，上游零改动 |
| bat（Rust，本机无 cargo 工具链） | ✅ 全闭环，governance 分支，既有文档零改动 |

四条 P0 修复全部验证生效。新发现 10 条，最重要的一条：

- **`git mv` 时序陷阱（两仓独立同踩、双双自愈）**：定稿编辑先落工作区再
  `git mv`，提交 2 会装进旧版本——`git mv` 只搬暂存区内容。修法入 development.md：
  **定稿先 `git add`，再 `git mv`**。两执行者独立踩同一个坑，是多代理实测独有的
  信号：单个执行者无法区分「我的失误」还是「说明书的缺口」。

其余回填：非 Node/Python 仓运行时判定（按仓库工具链）、门禁载体三选（npm script /
Makefile / gate.sh，本机无 make 时 Makefile 也是死配置）、工具链缺失时 SKIP 段
判例（显式债务：条件执行 + 原因可见 + 待验收 + 重开条件，到位后必须清除）、
`doc/` 近名目录、负例注入至少两类。

## 第三轮：awesome（纯文档仓，矩阵最后一格）

| 测试 | 结果 |
| --- | --- |
| awesome（纯 Markdown，无运行时） | ✅ 全闭环，11 文件全部新增、上游零触碰 |

历轮修复的连环确认：第三轮的执行者正确引用了「属主意图优先」「只读克隆不挂 CI」
「负例注入两类」「复验输出贴进提交 2 的 commit message」「逐字节复制未动脚本 = 免跑
回归」——前几轮写进文档的规则，后续执行者确实读到并照做了。

回填三条：纯文档仓门禁最小版 = 裸 check-docs（覆盖面如实登记，不夸大）、门禁
可绿判据的时点（从零引入时在提交 1 后演示）、任务卡 slug 约定 ASCII。

## 已知的诚实边界

- **验证层是软件形状的**：四类验证、source-map、peer 依赖影响面分析对内容仓
  不合身。内容仓一旦挂上任何 linter（markdownlint / vale / link checker），
  「只认退出码」即对内容生效。
- **约束力只及「先读 AGENTS.md 的 agent」**：这是所有 prose 治理的物理边界。
  实际约束栈：约定（harness 自动载入 AGENTS.md）→ 上下文（开工必读）→ 机器
  （门禁）→ 共享内存（git）。定位为「跨会话可持续协作」而非多 agent 并行协作
  基础设施。
- **只读克隆无外部强制**：不 push 就没有真正的外部强制，现有机制（待办 + fork
  重开条件）是文档层最优解。
- 留观项（等真实使用触发再动）：上游克隆专门适用条目、浅克隆同步策略、
  development.md 微调的更正式登记协议。

## 定位演化

初版声称「多会话 / 多 agent 可持续协作」；三轮实测后对齐为「跨会话可持续协作
+ 主会话派子代理实现 + 门禁兜底」，并据此将「待审查」态从状态机移除（六态 →
五态，审查落「审查记录」节、不占状态）。声称的与实际交付的一致，是这次迭代
最重要的收获。

## 设计变更（2026-10-16，rsra 真实使用回灌）

rsra 仓的单会话闭环任务采用单提交收尾后，卡内「提交：hash」字段自引用无解——
本提交的 hash 提交前不可知，只能事后回填，15 个提交里 6 个是单行回填（40%），
且回填违反「入目录即冻结」。据此改设计：任务↔提交的锚定为**提交信息里的任务
ID**（建卡时已有，提交那一刻锚就成立，`git log --grep=T-…` 随时可查），卡不记
hash；收尾默认单提交，两段式降为长任务的可选项；门禁新增**幽灵提交号**检查
（终态卡 ID 必须在 git log 命中）与幽灵登记对称——提交忘带任务号不再静默失联。
注意：砍 hash 的正当理由是自引用与仪式成本，**不是「双写」**——hash 是内容寻址
指针，不腐烂；按「指针也是双写」砍下去会误伤基准提交、勘误引用、依赖链接。
test-gate 回归 11 → 13 组（26 用例）全过。
