# 开发与验证流程（任务闭环）

> 单个任务从建卡到入档的执行细则。协作规则总纲见根目录 AGENTS.md。
> 「完成」只认命令输出，不认自述。

## 任务状态机（五态进出）

| 状态 | 进入 | 退出 |
| --- | --- | --- |
| 草稿 | 建卡，目标 / 范围未定稿 | 验收标准可判定且影响面分析完成 → 进行中 |
| 进行中 | 分析定稿，开始实现 | 验证通过 → 收尾（自审，或主会话审查后收尾）；被阻塞 → 待继续 |
| 待继续 | 被外部依赖 / 环境 / 换手阻塞，交接说明写明恢复条件 | 条件解除 → 进行中 |
| 完成 | 收尾入档 `implemented/` | 终态，正文冻结 |
| 已取消 | 决策记录否决或需求消失，入档 `rejected/` | 终态，正文冻结 |

## 任务闭环

**需求输入 → 建卡 → 影响面分析 → 实现 → 验证 → 审查 → 收尾入档**

1. **建卡**：从 `docs/tasks/_template.md` 复制到 `docs/tasks/` 顶层，文件名
   `YYYY-MM-DD-<slug>.md`。必填：目标（一句话）、验收标准（可判定）、允许修改范围、
   基准提交；状态置「草稿」，任务 ID（默认约定 `T-YYYYMMDD-NN`）登记进
   `docs/project-status.md`——状态页只写有现存卡对应的 ID，未建卡的待办用文字描述。
   完成判据：check-docs 通过——无孤儿、无幽灵、枚举合法。
2. **影响面分析**（非文案级改动）：引用方全仓 grep（源码 + 模板 + 测试）、依赖方
   （源码 import **与直接依赖的 peer 声明**）、受影响文档与调用方；结论写进卡
   「环境与范围」，允许修改范围由分析结论推出，两者一致。定稿后状态转「进行中」。
3. **实现**：只改允许范围内的文件；范围外发现一律进「未做清单」另开任务；
   伴随跑与改动相关的快速检查（typecheck / 相关测试 / lint）。
   完成判据：diff 全部落在声明的范围内。
4. **验证**：跑总门禁命令（见 AGENTS.md 验证纪律），退出码 0；视觉类改动补改前 /
   改后截图（build 通过不构成视觉验收）；四类验证中缺环境的，在卡「未验证项」写明
   原因。纯文档任务的迭代期可用快门禁（裸 check-docs）做高频反馈，完成判据仍只认
   总门禁。完成判据：命令与结果摘要贴进卡「验证结果」节。
5. **审查**（主会话派子代理实现的场景，可选）：主会话（未参与实现）按需求符合度 /
   diff / 风险 / 验证证据过一遍，结论写「审查记录」；有问题退回实现，修复后重走
   第 4 步。审查不占状态——结论落记录节，卡保持「进行中」直到收尾。
6. **收尾**：任务卡填毕验证结果（含代码提交 hash）即定稿；状态置终态；`git mv` 入
   `implemented/`（完成）或 `rejected/`（已取消，目录不存在先 mkdir）。git 顺序
   敏感：**定稿内容先 `git add`，再 `git mv`**——`git mv` 只搬暂存区里的旧版本，
   先改后 mv 会把定稿留在工作区、提交 2 装进进行中版本，靠提交后 `git status`
   才能暴露。状态页登记撤销、基线更新（只留结论级信息）；同轮文档清理——误导内容
   就地修订、过程产物删除或归档。两段式提交，时序固定：**提交 1（本任务代码改动 +
   进行中态的卡——卡在建卡时已登记状态页，保证此提交点位门禁可过）、提交 2（卡
   定稿 + 目录移动 + 状态页）**。卡内验证结果只记提交 1 的 hash；提交 2 的 hash
   在冻结前不可知，由 git 历史自证；入终态后的复验门禁输出贴进提交 2 的 commit
   message。提交 2 发现内容错误：未推送且卡内无引用时可 amend 修复，否则追加修复
   提交。正文在入终态目录前定稿，冻结从入目录那一刻起算。完成判据：check-docs
   通过 + `git status` 干净。
7. **勘误**（事后触发）：终态卡被新证据证伪时，只在文末**追加**勘误节（日期 + 证据 +
   修正结论 + 回填提交号），正文保持冻结；结论影响现行行为的，同步修订对应活文档
   并在勘误节点名。完成判据：正文 diff 为零，新增仅勘误节。

## 四类验证，分别记录、互不替代

1. **本地可重复**（总门禁命令覆盖）；
2. **真实联调**（记录环境、账号角色、时间、结论）；
3. **真机 / 目标设备**（记录页面清单与问题）；
4. **部署验收**（记录部署版本与核对项）。

第 1 类通过不等于 2-4 类已验证；缺环境时在任务卡「未验证项」和状态页「待验收」
登记并明说，不得宣称完成。

## 常见翻车点

- **范围外诱惑**：顺手发现的问题写进「未做清单」就继续——一行记录换一个专注的任务，
  别开新工。
- **终态卡顶层滞留**：收尾忘了 `mv`，门禁会拦（终态留顶层 = FAIL）；看到 FAIL 就移。
- **幽灵登记**：状态页登记的 ID 没有对应卡——门禁会拦；先修卡或删登记，
  不要为了过门禁倒填一张空卡。
- **提交夹带**：一次提交只 add 本任务相关文件；工作区的无关改动（生成物、本机环境
  差异）留在原地并在交付说明里点名。
- **状态页双写回潮**：状态页只留结论级信息（最近 2-3 条 + 指向任务目录的链接），
  细节归任务卡——目录即清单，第二份副本必然腐烂。
- **Windows 行尾噪音**：autocrlf 下 `git add` 的 LF→CRLF warning 是本机配置噪音，
  不是验证失败信号，无需处理。
